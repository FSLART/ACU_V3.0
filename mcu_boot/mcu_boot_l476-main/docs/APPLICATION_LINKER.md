# Create a new STM32 application project for this bootloader

**Configure the application's flash address, flash limit, stack and interrupt vectors once. Then build and upload its normal `.bin` for every update.** For the current STM32L476RG configuration, the application starts at **`0x08010200`**, has **`0x6F5D8` bytes** of usable flash and reserves the last **8 bytes of SRAM1** for bootloader entry.

This guide explains the GNU `.ld` scripts generated by STM32CubeIDE. The method applies to other STM32 targets after adapting their bootloader layout. Use the exact chip's memory map; copying the L476 addresses into another chip is not a port. Keil scatter files and IAR `.icf` files require the same reservations using their own syntax.

For a complete MCU port, use [PORTING.md](PORTING.md). For programming, use [UPLOADER.md](UPLOADER.md).

## Quick recipe for the existing L476 bootloader

In your **new application project**, rather than the bootloader project:

1. Copy its generated flash linker script to a project-owned file, for example `STM32L476RG_APP.ld`.
2. In its existing `MEMORY` block, change application `FLASH` to:

   ```ld
   FLASH (rx) : ORIGIN = 0x08010200, LENGTH = 0x6F5D8
   ```

3. Change SRAM1 `RAM` to:

   ```ld
   RAM (xrw) : ORIGIN = 0x20000000, LENGTH = 0x17FF8
   ```

4. Keep the stack definition outside `MEMORY`:

   ```ld
   _estack = ORIGIN(RAM) + LENGTH(RAM);
   ```

   It now evaluates to **`0x20017FF8`**, an eight-byte-aligned stack top. The bootloader request word remains at **`0x20017FFC`**.

5. Keep `.isr_vector` first in `FLASH`, and keep the generated sections and startup symbols.
6. Select your new `.ld` file in **both Debug and Release** linker settings.
7. Configure application startup to use **`VTOR = 0x08010200`** and preserve the selected flash-bank mapping.
8. Clean/rebuild, check the map and vectors, then pass the application's `.bin` to `can_upload.py`.

The remaining sections explain each step and how to calculate values for another STM32.

## 1 — Understand the three flash addresses

The uploader adds a header before your raw application. The linker must account for that header when assigning execution addresses.

```text
Physical image slot
+----------------------+-------------------------------+------------+-----------+
| MCUboot header       | Your raw application          | Hash TLV   | Metadata  |
| added by uploader    | vectors, code, constants,     | added by   | reserved  |
|                      | initial values for RAM data   | uploader   | by loader |
+----------------------+-------------------------------+------------+-----------+
^                      ^
SLOT_START             APPLICATION_START = SLOT_START + HEADER_SIZE
```

| Name | Purpose | Current L476 value |
| --- | --- | --- |
| Flash base | Bootloader reset/start address | `0x08000000` |
| Bank-1 slot start | Packaged image header address | `0x08010000` |
| Application start | Raw application's vector table and linker origin | `0x08010200` |
| Bank-2 slot start | Other physical storage slot | `0x08090000` |
| Bank-2 physical vectors | Storage address before bank remapping | `0x08090200` |

**Use the application start as your application's `FLASH ORIGIN`.** Linking at the flash base would overlap the bootloader. Linking at the slot start would put the vector table where the bootloader expects the header.

For current A/B remapping, keep **one application linker address** for both banks. When bank 2 is selected, the bootloader remaps it to the same logical execution address. Do not change the application's origin to `0x08090200` for alternate uploads.

On a different STM32, this requires a working target-specific bank-selection/remapping implementation. If there is no suitable remapping, choose a fixed execution slot with an installer, or separately linked images; linker changes alone cannot make the current A/B mechanism work. See [porting step 2](PORTING.md#step-2--choose-a-supported-update-strategy).

## 2 — Calculate the addresses and sizes for your target

Get the slot layout from the **ported bootloader**, its configuration headers and the chip's reference manual. An application project does not decide these independently.

Fill in this worksheet before editing:

| Value | Meaning | Your target |
| --- | --- | --- |
| `F` | Logical flash base used for application execution | |
| `O` | Execution slot offset from `F` | |
| `S` | Entire image slot size, including header and reserved metadata | |
| `H` | Packaged image header size | |
| `E` | Flash space reserved after the uploaded image for metadata | |
| `T` | Maximum complete trailing TLV block for the selected image format | |
| `A` | Application vector-table address | |
| `L` | Maximum raw application size | |
| `R`, `N` | Start and size of the RAM region used for the initial stack | |
| `Q` | Reserved RAM size for the bootloader request, including alignment/cache needs | |

For this bootloader's current unsigned header/payload/TLV format:

```text
A = F + O + H
Maximum packaged upload = S - E
L = S - E - H - T
Application FLASH: ORIGIN = A, LENGTH <= L
```

Current L476 example:

```text
F = 0x08000000
O = 0x00010000
S = 0x00070000       448 KiB slot
H = 0x00000200       512-byte header
E = 0x00000800       entire final 2 KiB erase page reserved
T = 0x00000028       complete 40-byte SHA-256 TLV block

A = 0x08010200
L = 0x70000 - 0x800 - 0x200 - 0x28 = 0x6F5D8 = 456152 bytes
```

The raw application may extend up to **`0x0807F7D8` exclusive**. The 40-byte TLV can then end at **`0x0807F800`**, where the reserved metadata page begins. The commit record is at the end of that page, but the **whole page** is excluded from uploads.

For different erase geometry, use the actual reserved erase region. Also account for any extra programming-alignment padding required by your port. Signed images need a larger TLV allowance; recalculate `T`, the linker limit and uploader checks together. The values above are for the unsigned implementation currently in this repository.

**Do not use the chip's total flash size as the application length.** That would allow code to occupy another slot or the bootloader's metadata.

## 3 — Select the correct linker script in CubeIDE

1. Create the application project for the exact MCU and generate its normal startup/HAL files.
2. Find its generated **flash** linker script, normally named `STM32<device>_FLASH.ld`.
3. Make a project-owned copy, such as `STM32<device>_APP.ld`, and edit that copy. Keep the chip-generated script structure.
4. Open **Project Properties → C/C++ Build → Settings → MCU GCC Linker → General** and select the application script. Labels can vary with CubeIDE version.
5. Apply the setting to Debug and Release, or use the appropriate all-configurations selection.
6. Check the build console: the link command's **`-T`** option must name your application script.

If you also use CMake, update the application target's linker-script path there. CubeIDE and CMake settings are independent.

Editing a file that the link command does not use has no effect. Recheck this after project regeneration or switching build configurations.

## 4 — Edit `MEMORY` and reserve the request flag

Keep all RAM regions generated for the target; change only the regions your layout requires. For the **L476 application**, this is a complete example `MEMORY` block:

```ld
MEMORY
{
  RAM   (xrw) : ORIGIN = 0x20000000, LENGTH = 0x17FF8
  RAM2  (xrw) : ORIGIN = 0x10000000, LENGTH = 32K
  FLASH (rx)  : ORIGIN = 0x08010200, LENGTH = 0x6F5D8
}

_estack = ORIGIN(RAM) + LENGTH(RAM);
```

Replace the original block; do not paste a second `MEMORY` block containing the same region names. GNU linker `K` means 1024 bytes; hexadecimal lengths make byte-level reservations clear. [GNU MEMORY documentation](https://www.sourceware.org/binutils/docs/ld/MEMORY.html).

The last eight SRAM1 bytes, `0x20017FF8` through `0x20017FFF`, are outside `RAM`. The application stack grows downward from `0x20017FF8`. The request word at `0x20017FFC` is excluded from normal stack, heap, `.data` and `.bss` allocations.

For another STM32 with suitable reset-retained RAM:

```text
Reserved block = [R + N - Q, R + N)
Usable RAM length = N - Q
Initial stack = an eight-byte-aligned address below the reserved block
Request word = an agreed four-byte-aligned address inside the reserved block
```

Use the **same request address and magic in the application and bootloader**. Reserve it in both projects and any RTOS/external memory allocator. `volatile` does not reserve memory. Startup code that clears all SRAM can still destroy it even when it is excluded from `.bss`.

On cached targets, select non-cacheable retained memory or reserve/clean the necessary cache lines before reset. Eight bytes is the L476 example, not a universal cache-safe reservation. Full function and retention requirements: [RequestBootloader instructions](PORTING.md#step-9--add-requestbootloader-to-the-application).

**Avoid the four-byte stack-alignment trap:** reserving only the final word and setting RAM length to `0x17FFC` makes `_estack = 0x20017FFC`. The current application's vector validator rejects that address because it is not eight-byte aligned. Use `0x17FF8` for this application example. The existing bootloader linker has a different four-byte reservation; do not copy its stack definition blindly into an application project.

## 5 — Keep the generated sections and vector table

Keep `ENTRY(Reset_Handler)`. It names the ELF entry point; it does not set the vector-table address or the MCU's power-on boot selection.

At the start of your existing `SECTIONS` block, retain the generated vector-table section. You can add a symbol and assertions to make mistakes fail during linking:

```ld
SECTIONS
{
  .isr_vector :
  {
    . = ALIGN(4);
    __app_vector_start__ = .;
    KEEP(*(.isr_vector))
    . = ALIGN(4);
  } >FLASH

  /* Keep the rest of your generated sections here. */
}

ASSERT(ADDR(.isr_vector) == ORIGIN(FLASH),
       "Application vector table must start at FLASH origin")
ASSERT((_estack & 7) == 0,
       "Application stack must be eight-byte aligned")
```

Insert these changes into your existing script. This is a section example, **not a replacement for the entire generated linker file**. If the startup uses a differently named vector section, use that actual section name instead.

Keep generated code/constants/unwind tables and C/C++ initialization arrays. Keep RAM initialization symbols such as `_sidata`, `_sdata`, `_edata`, `_sbss` and `_ebss` when your startup refers to them.

In particular, retain the application `.data` load mapping:

```ld
/* Typical CubeIDE arrangement; keep your target's existing startup conventions. */
_sidata = LOADADDR(.data);

.data :
{
  . = ALIGN(4);
  _sdata = .;
  *(.data)
  *(.data*)
  *(.RamFunc)
  *(.RamFunc*)
  . = ALIGN(4);
  _edata = .;
} >RAM AT>FLASH
```

This places initialized data in RAM while storing its initial bytes inside the application's flash region. `.RamFunc` is copied with it by the normal startup copy loop. If your target has a separate RAM-code section/copy table, keep that mechanism instead. [GNU address/alignment functions](https://www.sourceware.org/binutils/docs/ld/Builtin-Functions.html).

Review custom sections as well: fixed-address assets, persistent settings, external-flash sections, DMA buffers and independently located load images can bypass the normal `FLASH` limit. The current uploader accepts one contiguous application payload; widely separated load addresses can create a huge, mostly empty `.bin`.

## 6 — Make application startup keep the correct interrupt vectors

**Changing the linker alone is insufficient.** The bootloader sets the application vector address before handoff, but a new project's `SystemInit()` may change it back to the flash base. The app can reach `main()` and then fail on its first interrupt if vectors point into the bootloader.

For the L476 application, the intended value is:

```text
FLASH_BASE + VECT_TAB_OFFSET
0x08000000 + 0x00010200 = 0x08010200
```

Inspect the **application's** `system_stm32<family>xx.c` and startup sequence. Use one suitable mechanism:

### Option A — Use the target's Cube-generated relocation settings

For templates with the same controls as this L476 system file, enable:

```c
#define USER_VECT_TAB_ADDRESS
#define VECT_TAB_OFFSET 0x00010200U
```

These belong in the application startup configuration. Do not enable SRAM vectors for this flash-vector example. If supplied as compiler `-D` definitions, verify the generated source does not redefine them unconditionally. Update Debug and Release alike, and check the actual assignment to `SCB->VTOR`.

### Option B — Use the linker symbol in application `SystemInit()`

On a target with VTOR, the symbol from step 5 can avoid duplicating the vector address:

```c
/* The application's system file already includes its STM32 device/CMSIS header. */
extern uint32_t __app_vector_start__;

/* Inside application SystemInit(), after any generated vector-table assignment. */
SCB->VTOR = (uint32_t)&__app_vector_start__;
__DSB();
__ISB();
```

Use this before application interrupts can run, and ensure no later initialization changes VTOR. Preserve edits across Cube regeneration. Respect the exact target's vector-table alignment; the L476 example is aligned to `0x200`, but other cores/table sizes can require another alignment.

For cores without VTOR, implement their vector-copy/remapping mechanism and reserve the required RAM. TrustZone and multi-core STM32s need target-specific vector/handoff setup. Use [porting step 7](PORTING.md#step-7--adapt-jump-and-bank-remapping); this fragment is not valid unchanged on every STM32.

With current A/B remapping, use the **logical** vector address and preserve the selected bank mapping during application startup. Do not set VTOR to bank 2's physical storage address when that bank is already remapped to bank 1's logical address.

## 7 — Build the raw `.bin` and let the uploader add the header

Enable binary output/post-build conversion in your application project. The equivalent GNU command is:

```powershell
arm-none-eabi-objcopy -O binary YourApplication.elf YourApplication.bin
```

The binary starts with the application's vector table. The linker address is recorded in the ELF and encoded references; the raw `.bin` itself does not contain a destination-address field.

For this workflow:

- Do not prepend a header in the linker script; the uploader adds it.
- Do not add a 512-byte blank prefix to the raw `.bin`.
- Do not use `--pad-to` to fill the slot; the uploader expects an unpadded image.
- Do not pass the bootloader `.bin` as the application.

The uploader cannot relocate a binary linked for the wrong address. For another MCU port, update its RAM/vector checks and image-size limits together with the bootloader; they are currently L476-specific.

Normal CAN programming example, from the bootloader repository root:

```powershell
.venv\Scripts\python.exe tools/can_upload.py "C:\path\to\YourApplication.bin" --channel COM5
```

ELF debugging through ST-LINK is a separate workflow. Loading a raw application ELF does not create the packaged header/hash/commit metadata expected by this bootloader. To test handoff, first install a valid image through the uploader, then attach with the matching ELF symbols without erasing or overwriting the bootloader/slots. See the [CubeIDE user guide](https://www.st.com/resource/en/user_manual/dm00629856-stm32cubeide-user-guide-stmicroelectronics.pdf) for linker/debugger configuration.

## 8 — Verify before programming

### Check the build and map file

Check these in the application ELF/map, including any flash load addresses for RAM sections:

| Check | L476 example |
| --- | --- |
| Link command uses the intended `.ld` | Your application script, both build configurations |
| `.isr_vector` starts at application origin | `0x08010200` |
| All application flash load bytes stay below the raw-image limit | End address no greater than `0x0807F7D8` |
| Initial stack is in valid RAM and eight-byte aligned | `0x20017FF8` |
| Request word lies outside ordinary allocations | `0x20017FFC` |
| Raw binary fits its limit | At most 456152 bytes |

Useful inspection commands:

```powershell
arm-none-eabi-objdump -h YourApplication.elf
arm-none-eabi-nm -n YourApplication.elf
```

Use `objdump`'s **LMA** column when checking the flash load image for sections whose **VMA** is in RAM. An application may use little code yet still exceed flash because initialized data consumes flash too.

### Check the first two binary words

The first word is the initial stack pointer. The second is the Thumb reset-handler address. Run this from the repository root to apply the current uploader's packaging and vector checks without sending any CAN messages:

```powershell
.venv\Scripts\python.exe -c "import sys; from pathlib import Path; sys.path.insert(0, 'tools'); from can_upload import prepare_image; p = Path(sys.argv[1]); image = prepare_image(p.read_bytes()); print('Checks passed; packaged size:', len(image))" "C:\path\to\YourApplication.bin"
```

For this L476 configuration, expect an aligned stack in the configured SRAM ranges, a reset-handler address with bit 0 set, and its remaining address bits inside the application payload starting at `0x08010200`. A passing vector check does not prove all code references/startup behavior are correct; inspect the map and test interrupts on hardware too.

## Troubleshooting

| Symptom | Likely cause / check |
| --- | --- |
| Uploader says application vectors are invalid | Wrong flash origin, wrong binary, unaligned stack or host checks not ported |
| App reaches `main()` then faults | Startup restored VTOR to bootloader address; check interrupt vectors |
| `.isr_vector` still appears at `0x08000000` | Build uses another linker script/configuration |
| Works in bank 1, fails in bank 2 | Application uses physical bank-2 references or startup undoes remapping |
| RAM request does not enter bootloader | Flag overwritten by stack/startup/allocator, not retained or not flushed from cache |
| Raw `.bin` is unexpectedly huge | A section's load address is far from the application origin; inspect LMA |
| Linker reports flash overflow | App plus RAM initialization bytes exceeds the calculated payload budget |
| Reset under debugger runs the loader | MCU reset starts the bootloader; use its normal entry/selection flow or a deliberate app-debug launch |
| Debug works, Release fails | Different linker/startup definitions or missing `KEEP`/startup sections |

## Final checklist

- [ ] The bootloader port defines the target's actual slot and execution strategy.
- [ ] Application `FLASH ORIGIN` includes the packaged header offset.
- [ ] Application `FLASH LENGTH` excludes header, TLVs and reserved metadata.
- [ ] Debug and Release use the intended application linker file.
- [ ] Vector table is first in the raw image; generated startup sections/symbols remain intact.
- [ ] Stack and shared request flag reservations are correct in both programs.
- [ ] Application startup retains the correct vectors and selected bank mapping.
- [ ] ELF/map/load addresses and raw binary pass inspection.
- [ ] Upload, reset, interrupts and both-bank execution have been checked on the target board.

Once this setup works, keep the linker address fixed for normal A/B updates. Change it only when intentionally changing the bootloader's memory layout and updating both sides together.
